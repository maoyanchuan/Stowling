## 一、已确认的目标和范围

用户需要按固定栏位锁定背包，不需要“某物品保留多少件”的保护方式。

1. 锁定格整格跳过，未锁定格中的物品全部尝试存入。
2. 同种物品放在不同格子时分别处理，不按物品 ID 合并保护。
3. 锁定绑定格子位置；玩家手动移走物品后，锁仍留在原格。
4. 空格也能锁定，后来进入该格的物品同样受到保护。
5. 锁定格中的物品可以照常使用或消耗；锁定主要约束本 Mod 的自动搬运。
6. 数量仍可显示、统计，其他任务明确的业务数量仍可保留，不能再作为锁定依据。

本次存入改造覆盖现有掉落物拾取中的普通缓存存入，拆成可复用的执行模块。
复用现有任务入口、缓存配置和导航能力。

完整工作流：

```text
检测到掉落物
    → 前往拾取
    → 背包无法继续接收剩余掉落物，或者区域内掉落物已清空
    → 依次打开缓存，存入未锁定栏位的物品
    → 未锁定栏位存完后，再检查掉落物
    → 有掉落物则重复；区域为空且没有待存物品、没有在途操作时结束
```

原地能操作缓存时直接开箱。开箱期间新进入未锁定格的物品继续补存。
已确认满的缓存，在同一任务的后续批次中跳过。
所有缓存都无法接收剩余待存物品时，停止继续拾取并报错，物品留在背包中。
最后一件物品刚好填满最后一个缓存时，正常完成任务。

## 二、为什么需要修改现有实现

当前保护配置保存的是物品身份和数量，接口使用 `key + keepCount`。
浏览器虽然展示格子，实际保护与存入资格仍按物品总量计算。

普通存入目前还会比较：

```text
箱内增量 == 背包减少量 + 同期拾取回执量
```

一次轮询不相等，就可能关闭缓存并重新读取。
`MinecraftContainerTransferPort.beginResynchronization()` 会把 `avoidPickups` 设为 true，
然后重新寻路到不会吸入掉落物的位置。

新版日志已经确认：短暂的背包更新与拾取回执差异会触发该分支，造成重复侧移。
这不是启用了实验性打包，也不是拾取寻路没有取消。

目标是让普通存入根据未锁定栏位和服务器槽位同步推进，
不再用拾取回执与箱内增量的即时相等作为继续存入的条件。

## 三、实现顺序

### 1. 栏位模型与锁定存储

- 使用主背包与快捷栏的稳定索引，覆盖 36 个栏位。
- 区分背包索引和容器界面槽位编号；开箱后必须正确映射。
- 获取栏位索引时核对玩家背包归属，使用已有槽位映射能力。
- 保存完整栏位快照，供界面和执行层使用，不能只在前端显示锁定标记。
- 持久化保存格式版本与 `lockedSlots`，重启、重登后保持锁定。
- 装备栏与副手沿用现有用途，不纳入普通缓存存入来源。

建议的新存储结构：

```json
{
    "schemaVersion": 2,
    "lockedSlots": [0, 8, 12]
}
```

锁定不阻止玩家手动操作，也不改变原版自动拾取的格子分配。
物品进入锁定空格后，自动存入仍然跳过该格。

### 2. 旧数据迁移

- 备份旧保护文件，不把备份或玩家本地数据提交到 Git。
- 等待第一次完整背包同步后再迁移，避免登录时的空快照导致锁定丢失。
- 旧数据没有栏位索引，无法精确还原原本想锁的格子。
- 用旧保护状态识别当前对应物品，将它们所在的格子转换为整格锁定。
- 同类物品分散在多格时，迁移结果可能锁定多个格子，页面需显示结果供用户调整。
- 迁移完成后只保存栏位锁定，不再按旧数量拆分保护某一格。

### 3. 背包页面和鉴权接口

- 保留现有背包网格和项目主题，点击格子后提供“锁定／解锁”。
- 空格保持可操作，锁定格显示清晰标记，支持键盘操作。
- 移除“保留自用数量”“保存数量分配”等编辑逻辑。
- GET 响应应完整表达 36 格及锁定状态，包括空的锁定格。
- PUT 改为提交 `revision、slotIndex、locked`，移除 `key + keepCount` 分配逻辑。
- 保留现有鉴权、栏位范围校验和 revision 校验。
- 任务运行时可查看，修改锁定保持在空闲或安全停止后进行。
- 按 `docs/ui/task-ui-prompt.md` 和已确认模板实现，不重画其他页面。

### 4. 普通存入模块

- 存入候选直接从真实的未锁定格生成，跳过锁定格和空格。
- 普通存入优先对整格执行快速转移。
- 箱子只能接收一部分时，让游戏转入能放下的部分，剩余物品留在原格，再换箱。
- 未锁定格与锁定格即使物品 ID 相同，也不能一起过滤或合并保护。
- 同一箱子仍有容量时复用已打开的界面，继续处理新增的未锁定物品。
- 拾取回执可继续用于日志、来源和统计，不再决定普通存入能否推进。
- 任务账本应根据实际操作结果更新，不能仅凭计划点击数量认定全部存入。

需要保留服务器确认，但要改变确认依据：

- 从服务器下发的槽位更新或完整容器快照确认本批操作已经处理。
- 将同步信息关联到当前菜单对象和操作批次，避免复用窗口编号造成误判。
- 当前 `ContainerSyncTracker` 只记录初次完整初始化，不能直接当作每批操作确认。
- 不能把客户端预测画面、两个客户端 tick 看起来不变，直接当成服务器确认。
- 背包边存边被补满时，允许总数量不下降，不能因此触发异常侧移。
- 短暂不同步在原地等待；确需重开箱获取快照时，仍保持允许原地操作。
- 只有当前站位不满足真实交互距离或配置站位时才寻路。
- 真正超时、界面失效或服务器未接受操作时，停止并给出具体原因。

### 5. 任务循环与其他背包操作联动

- 普通拾取是否结束，以区域掉落物、未锁定格和在途操作状态为准。
- `collected/managed` 汇总账本或拾取回执余额不能单独决定是否还有待存物品。
- 满箱记忆在同一任务内保留，重新开始任务时重新确认实际容量。
- 无空格但同类物品仍可堆叠的箱子，仍可接收对应物品。
- 去掉普通存入因短暂数量差异触发 `avoidPickups=true` 的逻辑。
- 检查错误后的收尾，避免发现所有缓存已满后又反复尝试相同满箱。
- 公共自动搬运统一过滤锁定来源格和锁定目标格，避免其他入口绕过锁定。
- 开箱可切换手持选择，但不得临时交换锁定格与其他格的内容。
- 自动进食可以消耗锁定格中的指定食物；补给的自用逻辑同步改为栏位规则。
- 原有补给后保留自用的操作，应记录实际食物落点，避免重新引入数量保护。
- 分类、打包、工具使用、补给及收尾需检查兼容性，保留各自明确的业务用途。

### 6. 日志与文档同步

- 导出日志记录 `lockedSlots`、实际来源格、操作批次、服务器确认和换箱原因。
- 更新启动配置快照中的旧数量保护字段含义，避免导出仍声称按数量锁定。
- 浏览器日志继续显示简洁进度，完整诊断保留在导出文件中。
- 同步更新 `docs/container-interactions.md` 中普通存入的确认规则。
- 界面只调整本次业务控件；只有通用规范变化时才更新模板及项目提示词。

## 五、测试与验收

补充行为测试。Python 使用 pytest，Java 沿用项目现有 JUnit 结构。
不要用只匹配源码字符串的测试替代交互、状态迁移与存入结果测试。

| 场景 | 预期 |
| --- | --- |
| 同种物品分别位于锁定格与未锁定格 | 只存未锁定格 |
| 锁定格的物品数量、耐久或身份变化 | 锁定仍绑定该格 |
| 锁定空格、重启或重新登录 | 锁定状态保留 |
| 手动把物品移出锁定格 | 锁留在原格，物品按新所在格处理 |
| 旧数量配置迁移、登录初期空快照 | 正确迁移，不因空快照丢失锁定 |
| 打开不同容器界面 | 背包索引映射正确，不误操作锁定格 |
| 箱子只剩部分容量 | 能放多少放多少，余物留原格后换箱 |
| 箱子无空格但同类堆叠仍有容量 | 继续存入同类物品 |
| 边捡边存，背包总量不下降或回执暂时滞后 | 正常推进，不因此侧移 |
| 客户端预测成功、服务器撤销操作 | 不误报成功，不丢失待处理状态 |
| 后续批次卸货 | 跳过已确认满箱 |
| 所有缓存无法接收剩余物品 | 停止并报错，不再继续拾取或反复收尾开满箱 |
| 最后一件物品刚好填满最后一箱 | 正常完成 |
| 停止时存在未确认操作 | 等待安全结束，不遗留鼠标持有物 |
| 开箱换手、进食、补给及分类 | 遵守各自栏位约束 |
| 锁定接口未鉴权、索引非法或 revision 过期 | 拒绝修改 |
| 导出新日志 | 包含锁定栏位与实际操作来源格，浏览器保持简洁 |
