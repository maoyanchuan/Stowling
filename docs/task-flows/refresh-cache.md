# 刷新缓存任务

## 本轮依据与现有行为

- 用户要求：刷新缓存可选择分类区，分类区只打开储存区的箱子。
- 当前正式入口只列出普通区域，后端也拒绝手动刷新分类区。
  本轮保持普通区域执行行为，尚未把新增分类区行为认定为用户已验证的主流程。
- 共享执行器另有 `markerOnly` 内部步骤，供分类任务读取识别箱；
  也支持 `scanMarkers`、`includeMarkersInInventory`。这些隐藏能力不作为本轮主流程，
  不据此为手动刷新开放识别区开箱。

## 关闭实验开关时的执行基线

输入是一个真实普通区域引用、容器类型与手动／每日／间隔触发配置。
箱子、木桶、潜影盒默认启用，其他容器默认关闭。

1. 将所选区域按区块切片，按离玩家的水平距离排序。
2. 已加载区块直接扫描；未加载区块沿既有水平导航等待加载。
3. 按启用类型开箱，双箱去重，等待 Chest Tracker 更新记录。
4. 全部扫描结束后报告刷新数量；单箱失败继续后续容器，最终汇总失败。

输出为 Chest Tracker 库存缓存和任务结果。不搬运、分类或打包物品。
所有扫描和开箱成功为完成；断开世界、区块加载失败、开箱失败或缓存未更新为失败。
停止时取消当前导航与开箱，不再打开下一个容器。

## 调试改动：分类区仅刷新储存容器

- 标识：`refresh-category-storage-only`。
- 字段：步骤参数 `categoryStorageOnlyEnabled`，默认 `false`，缺失也为关闭。
- 状态：待验证；尚未并入主流程。
- 目的和阶段：在手动或定时刷新缓存的选区解析、扫描、开箱阶段支持分类区。
- 开启后的差异：分类区选区取全部绑定组的生效 `storageArea` 并集，
  保留原容器类型过滤、绑定组站位和双箱去重；只打开与储存区相交的容器，
  跨边界双箱从储存区内的一半打开。总选区、识别区与组间空隙不扩大扫描范围。
  即使旧参数要求扫描识别区，也不启用识别区扫描或更新分类标记缓存。
- 普通区域不受开关影响；分类任务内部 `markerOnly` 步骤继续使用原识别流程。
  本改动没有其他实验依赖或互斥，不修改公共扫描、导航、开箱策略。
- 分类区引用可选择和保存；开关关闭时保留引用，但阻止启动分类区刷新并说明开启方式。
  后端执行器同样拒绝未开启的分类区刷新，避免绕过 UI 后开箱。
- 开关放在任务底部“实验性设置”中，仅页面调试显示开启时显示。
  菜单默认收起，展开、运行状态、显示偏好和执行值分别维护。
  收起或隐藏不清空配置；任务收起时仍显示生效标识。

完成、失败和中断收尾沿用上述基线；无储存容器时正常完成，不回退扫描识别区。

## 调试改动：连续开箱复用安全手持槽位

- 标识：`refresh-reuse-safe-hand`。
- 字段：步骤参数 `reuseSafeHandEnabled`，默认 `false`，缺失也为关闭。
- 状态：待验证；尚未并入主流程。
- 依据：alpha.319 的本次诊断中，约 21 秒读取 36 个容器；每次开箱前重复等待
  安全槽位同步约 200ms。旧开箱逻辑在容器打开后恢复原槽位，下一箱再切换并等待。
- 目的和阶段：仅减少刷新缓存连续开箱阶段的重复手持切换和同步等待。
- 关闭时保持原有逐箱切换、等待、恢复行为。开启时创建本次刷新专用读取会话，
  首次选择空槽或镐并等待同步，此后保留该槽位；每箱仍校验手持安全，
  不跳过容器槽位同步和 Chest Tracker 缓存更新确认，不改变扫描、导航或开箱顺序。
- 正常结束、失败汇总、停止或世界断开时释放会话，关闭属于本次访问的容器，
  在原玩家仍可操作时恢复借用的背包槽与原快捷栏选择；断线后释放会话，不操作新玩家背包。
  单箱失败仍沿用原失败收尾，后续重新准备安全槽位。
- 普通区域和已启用分类区储存刷新均可使用；分类区仍须单独开启
  `refresh-category-storage-only`。两项分别控制开箱手持策略与扫描范围，互不覆盖。
  分类内部 `markerOnly` 刷新忽略本开关；其他读取、分类、存取任务保持原逻辑。
- 在底部“实验性设置”中提供独立开关；显示、展开、运行与执行值分别保存，
  隐藏或收起后仍保留已保存值和生效标识。
- 待用户游戏验证：连续读取速度、借用背包槽、单箱失败、取消与断线恢复；
  本地测试和构建不代表游戏验证通过，不自动合并主流程。
